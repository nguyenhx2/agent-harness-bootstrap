## 採点の土台になった主張

> モデルはコモディティ化しており、持続的な優位性を築く場所としては不向きだ。優位性は **エージェントハーネス**、
> **企業のコンテキスト**、**ワークフロー連携** に移る。ガバナンスは今や **プライバシー、知的財産、モデルの主権**
> を覆わなければならない。AI の能力を *どのモデルを使うか* で位置づけてはならない。**多数のモデル** を、
> ROI があり、データを管理下に置き、本番で安全に動くエージェントシステムに変える力として位置づけること。

## Gap 1 - モデルの主権: データには強制、ルーティングには助言

状態: 部分的に解消。

`model-policy.md` はデータ分類の表 (Public / Internal / Confidential / Restricted) を定め、各クラスを処理して
よいモデルに結びつけています。優先順位の規則は、分類が席の階層に勝つというものです。タスクのデータクラスが
その階層のモデルを許さないなら、作業は別の経路へ回されるか、そもそも委任されません。

その規則は `.claude/rules/` にあり、それは設定ではなくコンテキストです。Claude Code 自身の文書がはっきり
述べています。ルールは「Claude の振る舞いを形作るが、強制の層ではない」。したがってルール単体では、モデルが
従うことを選ぶ範囲でしか、モデルの主権を強制できません。

分類そのものに対する `settings.json` の deny ルールは配布していません。「Confidential のテキストをホスト型の
モデルに送った」ことは区別できるツール呼び出しではなく、deny ルールでは傍受できないからです。

### 強制されているもの

強制の対象は *モデル* ではなく *データ* です。Restricted なデータは既知のパスにあるので、`Read(<それらのパス>)` に
対する `permissions.deny` のエントリがあれば、エージェントはそもそもそのデータを手にしません。読めないものは、
どのプロバイダのどのモデルにも、どのモデルが動いていても、ルールを読んだかどうかに関係なく、漏らしようが
ありません。ガードレール評価が試しているのも同じ仕組みです。

実装する部品:

- `.claude/settings.json` は deny リストの先頭に `{{RESTRICTED_DENIES}}` のスロットを持つ。
- 導入時の質問で、Restricted なデータがどこにあるかをグロブパターンで聞く。
- `model-policy.md` は、分類の表が *方針* で、deny リストが *統制* だと明記している。

### まだ助言にとどまるもの

- **ルーティングそのもの。** 表が許さないモデルへ、Confidential だが読める文章をプロンプトとして渡すことを
  止めるものはありません。「このテキストをあのプロバイダに送った」という形のツール呼び出しがないので、
  フックが傍受できるものがありません。
- **組織が場所を特定できないデータ。** Restricted な資料に名前を付けられるパスがなければ、deny リストは
  それを覆えず、表は助言にすぎません。導入時の質問はこの事実の自白を強いますが、自白は統制ではありません。

現状の立場: このリポジトリはモデルの主権をデータの境界で強制し、それ以外の場所ではルールで統治します。

## Gap 2 - 多数のモデル: これは単一ベンダーのハーネス

主張は、多数のモデルをエージェントシステムに変える力を求めています。このリポジトリは Claude Code の上で
動きます。エージェント定義は Claude Code のフロントマター (`model:`、`effort:`、`tools:`、`maxTurns:`) です。
`model:` に使えるのは `opus | sonnet | haiku | fable`、つまり 1 社の 4 つのモデルです。

モデルの階層は入れ替えられます。モデルのベンダーは入れ替えられません。このロースターをセルフホストの Llama や
Azure 上の GPT に向け直すのは設定変更ではなく、移植です。

部分的に緩和するものが 2 つありますが、どちらも十分ではありません:

- `AGENTS.md` はベンダー中立の文書で、`CLAUDE.md` は薄い `@AGENTS.md` の import です。`AGENTS.md` を読むほかの
  コーディングエージェントはルールを得ます。しかしフックも settings の deny ルールも権限モデルも得られないので、
  助言は届いても強制は届きません。ファイルにもそう書いてあります。
- `model-tiers.md` の席の階層表 (判断 / 実装 / 機械的 -> モデル) は移植性にとって正しい形です。プロバイダを
  入れ替えるときに編集するのはこの 1 ファイルで、すべてのエージェントファイルを総なめにする必要がなくなる
  からです。ただし現状は Anthropic のエイリアスに対応づけているだけで、そこから何かを生成してはいません。
  エージェントファイルはまだモデルを直接名指ししています。スキャフォルダは両者が一致しているかを検査する
  ようになりました (`scaffold.py` の `seat_problems` が、`model:` が表の行と食い違う席を失敗にします)。
  そのため中途半端な総入れ替えは検出できますが、これは整合性の検査であって抽象化ではありません。

閉じるために必要なこと: 階層をエージェントが宣言するものにし、具体的な `model:` の値はスキャフォールド時に
階層表から生成する。スキャフォルダはすでにこの種の置換を行っています。そうすればベンダーの入れ替えは 1 ファイルの
編集と再実行で済みます。まだ実現していません。

最新のフックは、この文書がかつて主張したほどではないにせよ、この問題を助けるのではなく鋭くします。
`guard-agent-spawn` は Claude Code の `Agent|Task` ツールに結びついた PreToolUse フックです。最近まで、この
文書と `port.py` の両方が、Cursor にも Codex にも同等のサブエージェント起動のフックポイントはないと述べて
いました。**それはもう正しくありません**。Cursor は サブエージェントの種類に対するマッチャーつきの
`subagentStart` / `subagentStop` を備え、Codex も `agent_type` のマッチャーつきの `SubagentStart` /
`SubagentStop` を備えています。

Cursor の文書は、`subagentStart` が「サブエージェントの作成を許可または拒否できる」こと、終了コード 2 で
遮断できることを述べています。Codex のページは終了コード 2 による遮断を `PreToolUse`、`PostToolUse`、
`UserPromptSubmit`、`Stop` について挙げており、`SubagentStart` については述べていません。したがって Codex では
イベントの存在は確認でき、遮断の挙動は **未検証** です。この区別は残しておく価値があります。この節を書き直して
いるのは、以前に確認した以上のことを断定していたからです。

変わっていないのは、フックポイントがあることと統制があることは別だという点です。両者の間には 2 つの壁が
あり、どちらも配線ではなく実作業です:

- **ペイロードのフィールドが違う。** フックは `tool_input.subagent_type`、`tool_input.model`、
  `tool_input.prompt` を読みます。Cursor は `subagent_type`、`subagent_model`、`task` を、Codex は `agent_type` と
  `agent_id` を渡します。シェルや読み取りのイベントで Cursor アダプタがすでに行っているような、対応づけの
  アダプタが必要です。
- **ロースターの同一性が保たれないかもしれない。** 要となる検査は「`.claude/agents/<type>.md` が存在するか」
  です。Cursor が文書化しているサブエージェントの種類は `generalPurpose`、`explore`、`shell` で、名前付きの
  サブエージェントが自分の名前を報告するかは未検証です。Codex はエージェントの種類を Markdown の席ではなく
  `[agents.<name>]` という TOML のテーブルから取るので、ポーターがそのテーブルも出力しない限り、所属の検査は
  合いません。

したがって正直な言い方は **両方のツールで到達可能だが、どちらもまだ同等ではない** です。今日も境界は移植
されず、Cursor と Codex ではロースターはゲートではなく、モデルが読めるルールの文面のままです。以前との違いは、
これがツールに欠けた能力ではなく、形が分かっている移植作業になったことです。

## Gap 3 - ROI には分子がない

このリポジトリは、ハーネスが何を要し、何を節約するかを測っています。何を生み出すかは測っていません。
`benchmark/model_cost.py` は、1 機能がおよそ、既定のロースターで 2.52 ドル、全員 Haiku のロースターで 0.65 ドルだと
教えてくれます。しかし Haiku で作った機能が出荷に値するかは教えてくれません。

主張が成り立つかどうかを決めるのはそこです。優れたハーネスが安いモデルに許容できる成果を出させるなら、主張は
正しく、モデルの選択は本当にコモディティ化しています。そうでなければ、モデルの品質が依然として支配的で、
ハーネスは戦略ではなくコスト最適化にすぎません。

このリポジトリにはそれを測るものがありません。`eval/guardrail_eval.py` が測るのは下限、つまり安いモデルが
*できないようにされていること* だけです。上限 - 良いコードを書くか、Haiku のレビュアーが Opus のレビュアーの
見つけるバグを見つけるか - には、実際のタスク、実際の採点基準、API キーを使い、自分のリポジトリで走らせる評価が
必要です。その足場はここにはなく、その数字もリポジトリのどこにも載せていません。
## Gap 4 - 席ごとのモジュール範囲は誘導であってゲートではなく、Claude Code が公開しないデータなしにはゲートにできない

状態: 未解決。ただしこのバッチで「フックを誰も作っていない」から「フックはあるが構造上、上限がある」に変わり、
見かけより小さく、別の問題になった。

各開発エージェントのフロントマターには「Scope: あなたは `{{MODULE_PATHS}}` を担当する。その外のファイルは
変更しない」とあり、DDD ルールも同じ境界をドメインの言葉で繰り返しています (「境界づけられたコンテキスト」、
他のコンテキストの内部を import しない)。どちらも `.claude/rules/` かエージェントのフロントマターの散文で、
読まれるだけで強制はされません。

このバッチでは、`guard-agent-spawn` が起動境界を閉じたのと同じやり方でそれを閉じるために、`Edit|Write` への
`PreToolUse` フック `guard-agent-scope.sh` を配布しました。閉じてはいません。理由はフック自身のヘッダーが
説明しています。`Edit|Write` の `PreToolUse` ペイロードが持つのは `cwd` と `tool_input` (`file_path`、
`content`) で、呼び出しているサブエージェントを名指しするものは何もありません。`guard-agent-spawn` が門番になれる
のは、起動そのものに対して発火し、そこでは `tool_input.subagent_type` がペイロードだからです。起動された
エージェントが自分で `Edit`/`Write` を呼び始めると、その素性は消えます。`agent-history.sh` のヘッダーも逆側から
裏づけています。サブエージェントの素性が届くのは `SubagentStop` だけで、そのイベントには `tool_input` が
まったくありません。したがってこのイベントのフックは、「自分の持ち場の外を編集している間違った席」と
「オーケストレーター自身の文書メンテナンス」と「このプロジェクトに 1 人しかいない開発エージェント」を見分け
られません。存在しないデータに基づいて遮断すれば、正当な書き込みを無差別に止めるか、黙って何もしないかの
どちらかで、どちらも正直な誘導より悪い。`protect-adr` は反例ではありません。呼び出し元が誰かを知る必要なく、
受理済み ADR の固定リストに対する `file_path` だけで遮断します。モジュール範囲の強制に欠けているのは、
まさにその性質です。

代わりにフックが行うこと: `/code-graph` のモジュール担当マップと、進行中の唯一のタスクが宣言した範囲を使い、
編集されたファイルが別のエージェントの担当モジュールにあり、かつ Active なタスクがそれを挙げていないときに
`hookSpecificOutput.additionalContext` を出す - 遮断はしない。状況が曖昧なとき (グラフがまだない、Active な
タスクが 0 件または複数、担当なしのモジュール) は、推測せず黙っています。終了コードは常に 0。実在し、テスト済み
(評価の許可ケース 2 件がこれを検査) で、役に立つ信号です。しかし、以前のこの文書が単に未実装と言っていた
ゲートではなく、今後そうなることもありません。

本当に閉じるために必要なこと: このリポジトリが制御できない Claude Code のペイロードの能力、つまり起動以外の
ツール呼び出しにおける呼び出し元の素性です。それが実現するまで、`guard-agent-scope` の誘導が上限であり、
もう少しコードを足せば届くゲートへの踏み石ではありません。

今回追加したスキルの導入経路は、同じパターンの 3 度目です。`reference/skill-discovery.md` の信頼度ルーブリックも、
配線時の `/skill-wire` の再レビューも、「スキルの全ファイルを読み、秘密へのアクセス、外部へのデータ送出、
`.claude/`・`settings.json`・フックの編集指示がないか確かめる」ことが中心です。しかしその読み取りはコマンド
ファイルの手順であり、審査しているスキルをこれから信頼しようとしているモデル自身が行います。`.claude/skills/` が
後のターンが従う内容になる前に、候補スキルのファイルをこれらのパターンについて解析するフックはありません。
ゲートは `AskUserQuestion` と変更履歴の 1 行であって、技術的な統制ではありません。審査が雑だったスキルは、
モデルが従うことを選んだルールと同じだけ信頼されます - 衣装を変えた Gap 1 の問題です。

今回加えた `env-read.py` は、同じ問題の 4 つ目の衣装です。`protect-secrets` は広く知られた経路 -
`.env*` パスへの `Read`/`Edit`/`Write`、およびそれに対する `cat`/`type`/`head`/`Get-Content` にあたるシェル
コマンド - を厳格に遮断するので、これは助言ではなく強制された統制です。しかしエージェントに
`env-read.py` を通らせるものはありません。ほかの方法でファイルを開く Bash コマンド (短い Python や Node の
ワンライナー、サブプロセスとして呼ばれるテキストエディタ、正規表現の挙げていない名前のツール) はフックが
認識する形ではなく、「`env-read.py` を使え」というルールは `.claude/rules/agent-guardrails.md` の散文で、読ま
れるだけで強制されません。このスクリプトはエージェントが選んだときに確かに安全な既定値です (値は表示されず、
本番の名前は拒否される)。しかし溝は閉じません。不注意なエージェントが自分で考え出さなければならない範囲を
狭めるだけです。

## Gap 5 - tech-presets は、誰も鮮度チェックを走らせなくなった途端に腐る

状態: 未解決。別の問題を閉じるファイルが新たに持ち込んだもの。

`reference/tech-presets.md` はコードベース分析にバージョンの鮮度を持つカタログを与え、新しいモデルが古い学習
データのフレームワークのバージョンを提案しないようにしています。`codebase-analysis.md` はそれを正直に保つ
はずの規則を述べています。実際にインストールされているものが常にプリセットに優先し、バージョンは記憶ではなく
レジストリに照らして確かめ、導入済みの現実と食い違うプリセットは、黙って書き換えるのではなく移行の提案に
なる、というものです。

その規則は、モデルが読み、(たいてい) 従うテキストです - この文書のほかのすべての Gap と同じ形です。
`tech-presets.md` 自体を、ある周期で外の世界に照らして再確認するものはありません。固定したバージョンを
パッケージレジストリと突き合わせるスクリプトも、一定の年数を過ぎてそのまま使ったブートストラップを遮断する
フックも、ファイルを古いと印を付ける CI ジョブもありません。一度出荷され、以後のブートストラップがすべて
信頼するカタログは、書かれた日には正確で、1 年後には黙って間違っている種類の内容です。鮮度の *規則* は
実在しますが、鮮度の *確認* は自動化されていません。

閉じるために必要なこと: `tech-presets.md` の固定バージョンの標本を各パッケージレジストリと突き合わせ、差が
しきい値を超えたら (ブートストラップ自体は失敗させず - ネットワークに依存すべきではない) 定期ジョブを
失敗させるスクリプト。`/board-audit` がタスクボードのずれに使っている「信頼するが定期的に検証する」と同じ形です。

## 今日このリポジトリが支えていること

1. **ハーネスの安全性はモデルに依存しない。** 証明済みで再実行できる。250/250
   (両フック形式で 500/500)。`hooks_strict`、`long`、`db` を有効にしてスキャフォールドしたハーネスでの測定で、
   フラグの組は `eval/guardrail_eval.py` の `VARS` にある。
2. **ハーネス自体は導入も運搬も安い。ただし前回ほどではない。** 測定値: 読むのが 24% 減 (45% から下がった -
   スキルが圧縮の追いつくより速く機能を増やした。`benchmark/RESULTS.md` を参照)、書くのが 90% 減、ルール本文の
   73% が既定セッションの外、スキャフォールドは 1 秒未満。
3. **コストは既定ではなく決定である。** すべてのエージェントが明示的な `model:` と `effort:` を持つ。`model:` を
   未設定にすると `inherit` になり、機械的な作業が呼び出し側の階層で黙って課金されるので、品質ゲートはそれを
   バグとして扱う。
4. **既定のロースターは意図的に最安ではない。** `sonnet-only` (high) は約 20% 安い。既定は、その差額を
   Opus のレビューゲートに使う。生成の一手が間違えたものを捕まえることが仕事の席こそ、節約するのに最悪の
   場所だという論拠による。これは賭けであり、賭けだと明記しており、表を見れば反対側に賭けることもできる。
5. **ガバナンスは書かれ、版管理され、差分が取れる。** 決定的に強制できる部分 (秘密、PII、破壊的な操作、
   不変の ADR、コミットの衛生) はフックで強制する。`guard-destructive` は既定で配布する。より厳格な
   セット (大きなファイル、外部送信、固定されていない依存、プロンプトや出力の中の秘密、セッション途中の
   設定変更、証拠のない「完了」) は `hooks_strict` フラグの背後でオプトインであり、評価はそれを有効にした
   ハーネスを測っている。
6. **起動境界とループ防止の規律は、助言ではなくゲートである。** `guard-agent-spawn` は、ロースター外の
   種類の起動、起動時の席のモデルの上書き、登録済みの `TASK-NNN` も `TIER: direct` / `TIER: standard` の
   マーカーも名指ししない書き込み可能な席への委任 (Direct と Standard の作業には設計上タスクファイルがなく、
   Guarded の作業には登録済みのタスクが必要) を遮断し、それぞれに評価の許可ケースが対になっている。さらに
   検証台帳 (`.claude/state/verify-ledger.jsonl`、`verify-plan.py --dispatch-check` 経由) を読む。すでに通った
   内容へのレビューやスイートの再実行、3 回目のレビューラウンド、同一のブリーフ、タスクごとの委任予算
   (`dispatch_budget`、既定 24、`.claude/verify-map.json`) の超過を認めない。環境変数
   `CLAUDE_CODE_MAX_SUBAGENT_SPAWN_DEPTH` と `CLAUDE_CODE_MAX_CONCURRENT_SUBAGENTS` がファンアウトを抑える。
   `attempts:` の上限 (3 回で `Blocked`)、すべての席の `maxTurns`、`long` フラグ下の `retry-budget` フックが、
   行き詰まったエージェントが人の目に触れるまで動き続けられる長さを抑える。`/board-audit` は、これらの統制が
   構造上拾えない失敗モード、つまり孤立した Active タスク、記録されていない完了、ボードが登録していない
   ワークツリーを掃く。`guard-agent-scope` は起動境界の正直な兄弟で、ゲートではなく誘導であり、構造上ゲート
   にはなれないと明記している - Gap 4 を参照。
7. **ブートストラップ後の運用は、一度きりのスキャフォールドではなく、保守されるワークフローである。**
   `/harness-update` は変更されたコードベースに対してスキャフォルダを再実行し、差分のあるファイルを決して
   上書きしない - 衝突は人が解決する待ち行列に入り、黙って解決されない。`/harness-tune` は実際に起きた記録
   から出発し、制御レベルのダイヤル (デプロイ権限、deny/ask リスト、起動許可リスト、上限、レビューゲート) を、
   差分を見せて承認を得てからにだけ変更する。どちらも `harness-check.py` で終わり、それは終了コード 0 でなければ
   ならない。
8. **席は、盲目的に置くのではなく、審査済みの道筋でサードパーティのスキルを使って拡張できる。**
   `reference/skill-discovery.md` のルーブリック (インストール数、発行元の許可リスト、重複と監査のチェック、
   必須の内容確認) がインストールを関門にし、`/skill-wire` が配線時に再レビューし、設定編集を指示するスキルや
   レビュー席に書き込み前提の指示を渡すスキルを拒否し、すべての配線を記録する。それでもできないことは
   Gap 4 に書いてある。
