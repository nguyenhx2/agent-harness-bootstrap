# Agent Harness - プレゼンテーション構成案

[English](PRESENTATION-OUTLINE.md) · **日本語**

**この講演を一行で:** AI エージェントに、本当に理解できるリポジトリと、抜け出せないハーネスを与える。
**リポジトリ:** [agent-harness-bootstrap](https://github.com/nguyenhx2/agent-harness-bootstrap)
**スライド:** `presentation/index.html` - 26 枚、EN / VI / JA。この構成案にセクション単位で沿っています。
スライドはこの台本のビジュアルであって、もう一つの写しではありません。主張が変わったら、両方を変えてください。
**所要時間:** 40 分 (講演 28 分 + デモ 8 分 + 質疑応答)。短縮版と拡張版は末尾にあります。

---

## 全体の流れ

> エージェントが失敗するのは、リポジトリを理解していないか、止めるものが何もないからだ →
> 実際のリポジトリではこう見える → 答えはハーネスで、全体はこうつながる →
> チームが口にする 7 つの問いと、それぞれに答える仕組み → 仕組みの中身と、Claude Code で実地に走らせて
> 分かったこと → 証拠 → はじめ方。

まず考え方、次に痛み、最後に製品。問いが講演の背骨です。どれも聴衆自身が口にしたことのある一文で、
その直後にそれに答えるものが来ます。デモは後半に置きます。何を見ればよいかを聴衆が分かってからです。

## 0. 考え方 (2 分) - スライド 1-2

何よりも先に、二つの半分を言います。この後のすべては、そのどちらかです。

| 半分 | リポジトリの中で意味すること |
|---|---|
| **本当に理解できるリポジトリ** | 安定した ID を持つ書かれた契約。リポジトリの目的に合った規模のチーム。適用されるときだけ読み込まれるルール。ディスク上のタスク状態。だからウィンドウを閉じても何も失われない |
| **抜け出せないハーネス** | ツールが動く前に終了コード 2 で止め、自身が失敗しても遮断するフック。拒否リスト、席ごとのツール許可リスト、エージェント生成の深さの上限。どれもモデルの同意を求めない |

**決めの一言:** *「問題はモデルが賢くないことではない。モデルの周りが何も設計されていないことだ。」*

## 1. 課題 (4 分) - スライド 3-4

ハーネスのないエージェントが実際のリポジトリでやる 5 つのことを、1 枚ずつのカードで示します。
**読むべきでないものを読む** (バグ修正中に `.env`)、**担当外を編集する**、コンテキストが圧縮されて
**計画を忘れる**、**通過済みのものを再実行する** (README の誤字 1 つに全テストと全レビュアー)、
**証拠なしで「完了」と言う**。どれも、より賢いモデルでは解決しません。

**人の側の話にも時間を取る:** 不安定なのはモデルだけではありません。プロンプトの書き方は標準化されて
おらず、自然言語は情報が欠けるインターフェースで、どう頼んだかは git に残らず、引き継ぎのたびに
新しい翻訳が起きます。ハーネスを通すと、自由な言葉が入るのはインテークの **一度だけ** で、それが契約に
なります。その後の引き継ぎはすべてファイルです。*「人により良いプロンプトを書かせたいのではない。
プロンプトがインターフェースであることをやめさせたいのだ。」*

引用のスライドで締めます: *速さは優位を生む。目的地へ導くのは、制御である。*

## 2. 答え (3 分) - スライド 5-6

**スライド 5 は全体図** です (`docs/assets/harness-overview.ja.svg`。英語とベトナム語のスライドでは
`harness-overview.svg`)。左から右へたどります。持ち込んだ材料が `spec-builder` に入り、1 つの契約に
なる。`harness-bootstrap` はその契約と **コードベースそのもの** を読み、6 つの部品 (ルール、フック、
エージェントのロスター、ルーティング、スキル、検証) を組み立てる。作業は状態をディスクに書く
(タスクボード、実行履歴、チェックポイント)。`harness-view` はハーネスとその状態を読む。

**スライド 6:** エージェント = アプリケーション、ハーネス = OS、SDK = ビルディングブロック、
モデル = CPU。フレームワークでは開発者がオーケストレーションを書き、ハーネスではモデルが計画を立て、
ハーネスがそれを軌道に保ちます。

## 3. チームが実際に口にする 7 つの問い (16 分) - スライド 7-16

スライド 7 は地図です。README の「解決する課題」にある 7 つの問いを、それぞれに答える仕組みと
結びつけて並べます。その後、問いごとに 1〜2 枚。

### 問い 1. 「自分のプロジェクトに合ったチームがほしい」 - スライド 8-9

既存のリポジトリでは、まずコードを読んで回答を事前に埋めます。そのうえで最初の問いは、
リポジトリが **何のためにあるか** です。

| 目的 | 席 | 検証の方法 |
|---|---|---|
| コード | 実在モジュールごとに 1 つの開発席、`code-reviewer`、`spec-guardian` | テストとコードレビュー。セキュリティレビューは差分が必要とするときだけ |
| 調査 | `researcher`、`checker` | すべての主張を、それを述べている出典までたどる |
| 戦略 | `strategist`、`researcher`、`checker` | 本当に異なる選択肢、採点前に固定した基準、結論を覆す前提 |
| 文書 | `writer`、`checker` | 出典に照らして正確で、リンクが解決する |

根拠から決めます。1 回の実行で入るのは 18席のうち3〜17席で、既定で全部入ることはありません。
目的は組み合わせられ、コード以外の目的はすべて 1 つの `checker` が担い、質問は最大 2 回にまとまります。

**スキル (スライド 9):** **探す** (スタックに合うものだけ。選ぶ前にファイルを読む)、**作る**
(`/new-skill` はまずスキルであるべきかを判断し、断るのも普通。その後テンプレート、トリガーケース、
`skill-check.py`)、**つなぐ** (`/skill-wire` が席の `skills:` プリロードに追加。未配線のままの
スキルは `harness-view` が報告)。

### 問い 2. 「安全にしたい。でも考えすぎやトークンの浪費は困る」 - スライド 10-11

**ルーティングのティア** を、左から右へ重くなるはしごとして示します。大半の変更は Inline か Direct です。

| ティア | 対象の変更 | 誰が実行するか |
|---|---|---|
| **Inline** | 質問、調べもの、ドキュメントや設定の修正、全体が見える修正 | メインセッション。サブエージェントもタスクファイルもなし |
| **Direct** | 単一モジュール、可逆、契約・スキーマ・認証・決済・インフラに触れない | 担当の席を直接呼ぶ |
| **Standard** | 複数ファイル、または番号付き要件がある | 担当の席。圧縮を越える必要があるときだけタスクファイル |
| **Guarded** | 複数の席を順に使う、またはスキーマ・認証・金銭・マイグレーション・デプロイ・個人データ | オーケストレーターを通る唯一のティア |

すべての席が `model`・`effort`・`tools`・`maxTurns` を固定し、`settings.json` が生成の深さと同時実行数に
上限を設けます。*「必要より重いティアを選ぶのは慎重さではなく欠陥だ。」*

**何も得られない検証は拒否される (スライド 11)。** 差分 → `verify-plan.py` が必要なゲートを挙げる
(ドキュメント修正にレビュアーは付かず、シークレットスキャンは常に走る) → ゲート → **検証台帳** が
通過を、検査した内容のハッシュで記録する。`guard-agent-spawn` は、通過済みの内容への再実行、
3 回目のレビュー、同一の指示書、タスクの予算を超えた割り当てを拒否します。再実行を強制できるのは
人間だけで、指示書に `REVERIFY: <理由>` と書いて 1 回限り、記録に残ります。

### 問い 3. 「キーの漏洩が心配」 - スライド 12

常時: `protect-secrets` (`.env.example` を除く `.env*`、鍵、`secrets/`、`credentials/` の読取と
コピーを、Bash でも PowerShell でも遮断)、`env-read.py` (値を読み込んだ状態でコマンドを実行し、
出力から値を伏せる)、`/secret-scan` (レビュー前に差分をスキャン)。`hooks_strict` では
`secret-guard` (プロンプト中のベンダー形式の鍵を送信前に遮断) と `guard-egress` (許可リストにない
ホストへの送信を遮断。プロンプトインジェクションが必要とする一手) が加わります。

### 問い 4. 「従来の SDLC は苦しく、AI-DLC は中途半端に終わる」 - スライド 13

仕様を判定基準にした 1 つのループ: **FR → タスク → 実装 → verify-plan → レビュー → 完了**。
誤りと分かった基準は、迂回せず仕様へ戻します。手続きは変更に従います。Inline と Direct は仕様作業なし、
Standard は合意済みの FR に基準を 1 つ追加、Guarded は新しい FR をまず確認
(`spec-builder/reference/agentic-loop.md`)。

### 問い 5. 「人が確認でき、AI が理解できる仕様がほしい」 - スライド 14

`spec-builder` はどんな入力も `docs/specs/` の 1 つの契約にします。コア6セクション常時、最大8セクションは任意で、
素材の中身で選ばれます。何か尋ねる前に、ソースごとの読み方を示します。契約は安定した FR ID と、
否定ケースを含む Given/When/Then 基準を持ち、見え方は 2 つです。`confirmation.md` (すべての FR を
平易な言葉で、PO が はい / いいえ / 変更 を答える欄付き) と `index.json` (エージェントが最初に読むもの)。
不明点は `AS-nn` か `OI-nn` になり、創作されません。`spec-check.py` が両方を再生成し、どちらかが
仕様に遅れたら失敗します。

### 問い 6. 「エージェントの動きを、細部まで理解して制御したい」 - スライド 15

`harness-view` はディスク上のものをモデルを介さずに読みます。エージェント・ルール・フック・コマンド・
モジュールのライブグラフ、ルール・フック・席を停止する切替 (保護された制御は人間が合い言葉を打つ必要
がある)、`agent-history` の実行履歴と、どのルールがなぜ読まれたかを記録する `agent-trace`。
`harness-check.py` はすべての相互参照が実在するものを指すことを証明します。

### 問い 7. 「出来上がると確認しきれず、採点も曖昧」 - スライド 16

`harness-view assess` は素朴なルールエンジンで、ブラウザのタブも CI も同じものが動きます。
重み x 件数 / 手間で並ぶ作業リスト、ワンクリック修正、前回からの変化、そして 6 カテゴリ (Safety、
Cost control、Traceability、Board health、Docs quality、Contract) の公開ルーブリック
(`tools/harness-view/RUBRIC.ja.md`)。スクリーンショットは実在のハーネスです。ノード 219、エッジ 655、
採点は 99/100。

## 4. 仕組み (8 分) - スライド 17-21

**コンテキストの階層 (スライド 17)。** ウィンドウは RAM、作業はディスクにあり、圧縮は設計上
生き延びられます。

| 階層 | そこにあるもの | 圧縮で起きること |
|---|---|---|
| **Always-RAM** | `CLAUDE.md`、無条件ルール 7 本、エージェント本体、ツールスキーマ | 毎ターン注入し直されるので残る |
| **Lazy-RAM** | 対象パス限定のルール 10 本と、モジュールごとの `CLAUDE.md` | 一致するファイルに触れたとき読み込み直される |
| **Disk** | ボードと、タスクごとに 1 ファイル: チェックポイントと上限付きのセッションログ | 何も起きない。コミット済みの markdown |
| **Archive** | 終わったサブエージェント実行ごとに 1 ファイル。`SubagentStop` フックが書く | 何も起きない。事後に書かれる |

`task.py move` はボードの行・ファイルの `status:`・フォルダを同時に変え、`task.py checkpoint` は
次の一手と最後に green だったコミットを書きます。新しいセッションは 3 行で再開します。
*「ウィンドウが閉じるのは事故ではない。想定どおりのことだ。」*

**あらゆるイベントのフック (スライド 18)** を、ライフサイクルの上に、遮断・警告・文脈の色分けで
描きます。SessionStart (`session-context`)、UserPromptSubmit (`secret-guard`)、PreToolUse
(`protect-secrets`、`guard-destructive`、`guard-main-commit`、`check-commit-msg`、`guard-agent-spawn`、
`guard-board`、`protect-adr`。strict で `guard-egress`、`guard-large-file`、`guard-deps`、`db` で
`guard-migration`)、PostToolUse (リマインダー、`retry-budget`)、PreCompact (`compact-checkpoint`)、
Stop (`stop-evidence`、`agent-history`)。**遮断ガードはフェイルクローズ** です。タイムアウトや
クラッシュしたガードは呼び出しを遮断します (`onFailure: block`)。助言フックはフェイルオープンのまま。
壊れたリマインダーが作業を止めてはならないからです。全表は
`harness-bootstrap/assets/claude/hooks/README.md`。

**多層防御 (スライド 19):** 拒否リスト (見えないもの)、フック (できないこと)、ツール許可リスト
(届かないもの)、`maxTurns` と生成の上限 (暴走)。弱点は自分から言います。拒否リストは前方一致で、
順序の入れ替えで破れます。減速帯であり、**ゲートはフックです。**

**Claude Code で実地に走らせる (スライド 20)。** v1.20.1 で初めてフックを実際の Claude Code
セッションの中で走らせ、スクリプトのペイロードでは見えなかった 4 つの穴を塞ぎました。

1. **git のグローバルオプション** - `git -c k=v commit`、`git -C . commit`、`git --git-dir .git push
   --force` がコミットと破壊操作のガードをすり抜けていた。今は読み通される。
2. **Windows の台帳** - Windows PowerShell 5.1 がペイロードの前に BOM を付け、台帳がすべての割り当てを
   通していた。修正済みで、読めないペイロードは遮断される。
3. **ガードはフェイルクローズ** - 負荷下でガードがタイムアウトし、`Remove-Item -Recurse -Force .` が
   実行された。今はすべての遮断ガードが `onFailure: block` を持つ。
4. **PowerShell 経由のシークレット** - PowerShell ツール経由の `Get-Content .env` は検査されて
   いなかった。今は `protect-secrets` が捉える。

ガードレール評価は、`.ps1` 版を settings が呼ぶのと同じ Windows PowerShell で、`.sh` 版を Git Bash で
実行するようになりました。

**1 つのハーネス、3 つのツール (スライド 21)。** ルールは `.cursor/rules/*.mdc` と `AGENTS.md` へ、
強制は `.cursor/hooks.json` (アダプタ付き) と `.codex/hooks.json` へ移植されます。限界は声に出します。
Codex は `apply_patch` で編集するので ADR ガードはベストエフォート、Cursor の `afterFileEdit` は
観測のみ、どちらにもサブエージェント生成のフックポイントはありません。

## 5. 証拠 (4 分) - スライド 22-24

**安全性の下限 (スライド 22):** `eval/guardrail_eval.py` はフック形式ごとに実物のハーネスを生成し、
289 のペイロードを撃ち込みます。must-block が 122、must-allow が 167 で、`.sh` でも `.ps1` でも
ガードレール評価は 290/290。`hooks_strict`、`long`、`db` を有効にした構成で、モデルへの問い合わせは
ありません。移植用アダプタの自己テストは 32/32。*「安いモデルでもシークレットはコミットできない。
分別があるからではなく、フックが終了コード 2 を返し、ツール呼び出しが起きないからだ。」* そして正直な
限界を言います。これは下限であって上限ではなく、測っているのはその構成のフックで、エージェントの
振る舞いではありません。

**すべての数値はスクリプト由来 (スライド 23)。** 文書がずれれば `scripts/check_numbers.py` が CI を
失敗させます。

| 指標 | 前 | 後 | 変化 |
|---|---:|---:|---:|
| Read path (bytes pulled into context) - コンテキストに読み込むバイト数 | 234,196 | 136,249 | -42% |
| Read path (files read) - 読むファイル数 | 24 | 10 | -58% |
| Write path (bytes the model must author) - モデルが書くべきバイト数 | 95,064 | 9,439 | -90% |

- ルール本文の 75% が既定のセッションに入らない
- 18エージェント、17ルール、23コマンド、26フック。1 回の実行で入るのは 18席のうち3〜17席
- ガードレール評価はフック形式ごとに 289/289

バイト数は正確な値、トークン数は 3.6 文字/トークンでの推定値です。

**実地ベンチマーク (スライド 24)** は、フィクスチャリポジトリ上の実際のエージェントセッションを、
ハーネスなしとありで比べます。数値はこのリリースのベンチマーク自身の出力から取り、スライドの `bench`
データ (要素 `#bench-results`) に入れます。それまでは仮置きと明示されています。出力にある数値だけを
示し、測っていないものも言います。

## 6. ライブデモ (8 分) - 予備はスライド 25

既存のコードがある実際のリポジトリを使います。説得力があるのはブラウンフィールドで、空のフォルダでは
ありません。

1. **(30 秒)** 導入前のリポジトリ: ソースはあり、`.claude/` はない。
2. **(90 秒)** `/harness-bootstrap`: まずコードを読み、目的を尋ね、各席のモデルと effort を含む計画を
   示す。まだ何も書かれていない。
3. **(30 秒)** 承認。ファイルごとに `ADDED` / `KEPT` / `CONFLICT` が報告される。
4. **(2 分)** **わざと壊す** - `cat .env`、`main` へのコミット、`main` での `git -c k=v commit`、
   Accepted の ADR の編集。すべて遮断される。講演はこの瞬間のために組み立てられています。
5. **(90 秒)** `python eval/guardrail_eval.py` をその場で。*「モデルには何も問い合わせていない。
   これは終了コードだ。」*
6. **(60 秒)** ドキュメントだけの変更に `python .claude/scripts/verify-plan.py`: シークレットスキャンだけ。
7. **(60 秒)** 新しいセッションで `/task-resume`: チェックポイントを読み、タスクの途中から再開する。

予備: ツールが動かない → スライド 25 のクリップ、次にギャラリー。時間が足りない → 6 と 7 を削る。
**4 と 5 は決して削らない**。

## 7. 締め (2 分) - スライド 26

エージェントはリポジトリを理解している。ハーネスから出られない。作業は変更に見合った分だけ検査される。

```
/plugin marketplace add nguyenhx2/agent-harness-bootstrap
/plugin install harness-bootstrap@agent-harness-bootstrap
/plugin install spec-builder@agent-harness-bootstrap

/spec-builder           # 先に契約を書く
/harness-bootstrap      # このリポジトリのハーネスを構築
```

1 画面の計画を承認するまで何も書かれません。リポジトリ、クリップのギャラリー、`docs/FLOWS.md` を示し、
希望者のリポジトリでその場で動かすことを申し出ます。

## 質疑応答の準備

| 質問 | 短い答え |
|---|---|
| *Claude Code に縛られるのか?* | いいえ。強制ごと Cursor と Codex に移植でき、`AGENTS.md` がベンダー中立の契約 |
| *すでに `.claude/` フォルダがある。* | 突き合わせるだけで上書きしない。違いは `CONFLICT` として返る |
| *うちのリポジトリはコードではなく調査だ。* | 目的プロファイル: 調査用リポジトリには `researcher` と `checker` が付き、出典で検証され、テストやコードレビューの席はない |
| *エージェントはフックを回避できるか?* | 拒否リストは回避され得る。減速帯だ。フックはツールが動く前に発火して終了コード 2 を返す。git のグローバルオプションも含めて |
| *フックがクラッシュしたり固まったりしたら?* | 遮断ガードはフェイルクローズで、呼び出しは遮断される。インタプリタが無い場合だけは警告して通す。何でも止めるガードは結局切られるから |
| *安いモデルにすると安全性は崩れるか?* | 崩れない。モデルには問い合わせず、ガードレールはシェルスクリプトだ。コード品質とレビューの深さは落ちる |
| *開発者の足を引っ張らないか?* | 小さな作業ではそうならない。Inline と Direct はオーケストレーターもタスクファイルも通らず、ドキュメントの変更にレビュアーは付かず、何も得られない再実行は台帳が拒否する |
| *要するに大きな CLAUDE.md では?* | CLAUDE.md は、圧縮の後にモデルが忘れるかもしれない助言だ。これは強制と、消えない状態だ |
| *方針の決定は誰が持つのか?* | あなただ。ガバナンスのルールは空欄で出荷され、ライセンス方針や分類表をスキルが勝手に作ることはない |

## ファクトシート

`scripts/check_numbers.py` が検査します。数値を手で直すのではなく、再実行してください。

- エージェント 18 席 (+1 dev-agent テンプレート)、ルール 17、コマンド 23、フック 26。1 回の実行で入るのは 18席のうち3〜17席
- 無条件ルール 7、対象パス限定 10。ルール本文の 75% が既定のセッションに入らない
- ガードレール評価はフック形式ごとに 289/289 (must-block 122、must-allow 167)。`hooks_strict`、`long`、`db` を有効化、モデルへの問い合わせなし。移植用アダプタの自己テストは 32/32
- spec-builder: コア 6 セクション、任意は最大 8
- ルーティングのティアは 4 つ: Inline、Direct、Standard、Guarded。オーケストレーターを使うのは Guarded だけ
- タスクの状態は 5 つ: `Planned`、`Active`、`Blocked`、`Pending`、`Done`
- モードは 4 つ: Greenfield、Brownfield、Audit、Update
- 目的は 4 つ: コード、調査、戦略、文書
- ルーブリックのカテゴリは 6 つ: Safety、Cost control、Traceability、Board health、Docs quality、Contract
