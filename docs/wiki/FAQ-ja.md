# FAQ

[[English|FAQ]] · **日本語**

## Claude Code でしか動かないのですか?

Claude Code 向けに作られていますが、移植できます。`python harness-bootstrap/scripts/port.py --target . --tool all`
は、ルールを Cursor の形式に変換し、フックを Cursor と Codex に登録します。Codex のフックのペイロードは
Claude Code のものと一致するので、フックは直接登録されます。Cursor には、ペイロードと応答を変換する
小さなアダプタが付きます。

移植で運ばれるのは、助言だけではなく**強制**です。アダプタは CI で、両方のフックの系統についてセルフ
テストされています。

## spec-builder は PDF、Word、Excel のファイルを読めますか?

読めます。そしてもっと重要なのは、読めない場合にそれが分かることです。渡したすべての情報源は、それを
実際に読める読み取り手に振り分けられます (`route_sources.py` がファイルごとに判断し、その理由を表示
します)。危険なケースは明示的に扱われます。スキャンされた PDF は「抽出」に成功したように見えて、ほとんど
何も返しません。これこそモデルが仕様をでっち上げてしまう経路です。そのため、1 ページあたり
80文字未満のものは、代わりに画像を読む処理に回されます。インストール済みのどれでも開けないファイルは、
どのファイルか、なぜか、何があれば直るかを示す、名前付きの未解決事項 (`OI-nn`) になります。黙った欠落にも、
推測にもなりません。

## 安全性は使うモデルによって変わりますか?

変わりません。そしてそれが中心となる主張です。ガードレールはシェルスクリプトと終了コードなので、
モデルには問い合わせず、結果がモデルに左右されることはあり得ません。`python eval/guardrail_eval.py` は、
strict フック、長時間セッション用フック、データベースガードを有効にして (`hooks_strict`、`long`、`db`)
組み立てたハーネスにペイロードを撃ち込みます。既定のインストールに含まれるフックはそれより少なく、
既定で同梱される strict 系のガードは `guard-destructive` だけです。

安いモデルで変わるのは、書かれるコードの質とレビューの深さです。それは上限の話で、評価はそれを測り
ません。モデルに依存しないのは下限の方です。

## ルールをプロンプトに書くだけではだめなのですか?

指示として書かれたルールは、飛ばされ得るからです。モデルが従うと選ぶことに依存するものはコントロール
ではなく、希望です。2 で終了するフックはコントロールです。

ハーネスは両方を意図的に使い、どちらがどちらかを明示しています。
[`docs/ASSESSMENT.ja.md`](https://github.com/nguyenhx2/agent-harness-bootstrap/blob/main/docs/ASSESSMENT.ja.md)
に、何が強制され、何が助言にとどまるかが一覧になっています。

## 既存の `.claude/` は上書きされますか?

されません。スキャフォルダは存在するファイルを決して上書きしません。`ADDED`、`KEPT`、`CONFLICT` を
報告し、`CONFLICT` の解決はあなたに委ねられます。あなたが書いたものは、あなたの承認なしには何も
削除されません。

## なぜエージェントがこんなに少ないのですか? 他のキットはもっと多く同梱しています。

それは不足ではなく、狙いです。[[テーラードビルド|Tailored-Build-ja]] を参照してください。誰も作業を
振らない席は、温存された能力ではなく、コンテキストの請求書であり、読みにくくなったルーティング表です。
一回の実行でインストールされるのは、リポジトリが何のためのものか、契約とコードベースが何を正当化するかに
応じて 18席のうち3〜17席で、それに実在するモジュールごとに dev エージェントが一つずつ加わります。

## 両方のスキルを使わなければなりませんか?

いいえ。それぞれ単独で成り立ちます。契約はハーネスをより良くし、ハーネスは契約を強制可能にしますが、
どちらか一方だけを実行できます。

## ルールとフックの違いは何ですか?

ルールはエージェントが読むガイダンスです。フックはツール呼び出しの前後に実行され、それをブロック
できるスクリプトです。ルールは振る舞いを形づくり、フックはそれを強制します。[[Rule Reference]] と
[[Hook Reference]] を参照してください。

## なぜほとんどのルールがパス限定なのですか?

毎セッション読み込まれるルールは、すべてのリクエストにかかる恒久的なコンテキストのコストだからです。
パス限定のルールは、一致するファイルに触れたときにだけウィンドウに入るので、ルール本文の大半を既定の
セッションの外に置いておけます。無条件で読み込まれるのは、本当に普遍的なルールだけです。

## エージェントがガードレールを無効にできますか?

できません。`/harness-toggle` はエージェントをはなから拒否し、安全上重要なコントロールは、「はい」では
なく人間が入力するフレーズを求めます。すべてのトグルはコミットされる `.claude/disabled.json` に記録される
ので、何かをオフにすることは、黙った変更ではなくレビュー可能な変更になります。

## 小さなプロジェクトには過剰設計ではありませんか?

そうかもしれません。そして質問票には、まさにそのための軽量な回答があります。儀式は最小限、方法論の
ルールなし、レビューゲートは維持。最も簡素なコードのビルドは六席で、調査やドキュメントのリポジトリなら
三席で済みます。
それでも多すぎるなら、
`rm -rf .claude/` でリポジトリは元どおりです。

## コードをどこかに送りますか?

スキルとツールはローカルで動きます。`harness-view` はネットワーク呼び出しを一切しません。Claude Code の
セッションが送るものは、あなたとプロバイダの間の話で、ハーネスはそこに何も加えません。そして
`model-policy` ルールは、どのデータ区分がどのプロバイダに届いてよいかをそもそも書き留められるように
するためにあります。

## この Wiki の主張が本当だとどうして分かるのですか?

その隣に書かれたスクリプトを実行してください。このプロジェクトでどこかに公開されたすべての数字は、
`python scripts/check_numbers.py` によってスクリプトと照合され、矛盾があればビルドが失敗します。この Wiki の
リファレンスページはアセットから生成されるので、それだけが独立してずれることもありません。
