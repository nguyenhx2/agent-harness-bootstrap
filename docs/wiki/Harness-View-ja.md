# Harness View

[[English|Harness-View]] · **日本語**

中身を確かめられないハーネスは、信じるしかないハーネスです。`harness-view` は実際にディスク上に
あるものを読み、描画し、採点し、その一部をオフにできるようにします。

**そのどこにもモデルは関与しません。** これは制約ではなく設計です。ブラウザと CI の実行が、
答えについて食い違うことはあり得ません。

## インストール

Windows、macOS、Linux 向けのビルド済みバイナリが、チェックサム付きで
[各リリース](https://github.com/nguyenhx2/agent-harness-bootstrap/releases/latest) に添付されています。
あるいはソースからビルドします:

```bash
cargo install --path tools/harness-view
```

ソースが正であり、バイナリは利便のためのものです。

## コマンド

```bash
harness-view scan   .    # .claude/state/harness-graph.json を書いて終了する
harness-view serve  .    # localhost でハーネスを閲覧する
harness-view assess .    # 採点し、ゲートに落ちたら非ゼロで終了する
harness-view watch  .    # ファイルの変更に合わせて再スキャンする
```

`assess` が非ゼロで終了することが、パイプラインで使える理由です。レビュアーがブラウザで行うのと
同じチェックが、ビルドを失敗させられます。

## 各ビューが見せるもの

**Flow** は、制御が実際に流れる順にコントロールプレーンを並べます。設定、フック、ルール、エージェントの
席、マージゲート、そして人間。「このリポジトリへの変更は、実際にどうやって抑えられているのか」に
一画面で答えます。

**Graph** は同じデータを力学レイアウトで表示します。順序ではなく、まとまりを見たいときに使います。

すべてのノードはファイルです。クリックすると、整形済みまたは生の実際の内容が表示されます。担当
エージェント付きのタスクファイルも含みます。

## Assess が採点するもの

エンジンは公開されたルーブリック (`tools/harness-view/RUBRIC.md`、日本語版は
[`RUBRIC.ja.md`](https://github.com/nguyenhx2/agent-harness-bootstrap/blob/main/tools/harness-view/RUBRIC.ja.md)、
`harness-view rubric` でも表示) に照らしてハーネスを検査し、各所見にルール ID、`file:line` 形式の証拠、
なぜ重要か、具体的な修正を付けます。六つのカテゴリは、安全性、コスト管理、トレーサビリティ、ボードの
健全性、ドキュメント品質、契約です。各カテゴリは 100 から始まり、そこに含まれる所見ごとにその重みが
差し引かれるので、スコアはルーブリックだけから再計算できます。ルールは、すべてのリポジトリ、コードの
リポジトリ、コード以外のリポジトリのいずれかに適用されます。目的は bootstrap が記録した `purpose_*`
フラグから取られるので、調査リポジトリがコードレビューのコマンドを追加しろと言われることはありません。

結果を行動に移せるものにしているのは二つです。**ワークリスト**は所見をルールごとにまとめ、
重み×件数÷労力の順にルールを並べ、各ルールを解消したら総合スコアがいくつになるかを示します。
**`--since prev.json`** (および前回のチェックを覚えているビューア) は、修正された所見、新しい所見、
動いたすべてのスコアを示します。

教えてくれることの例:

- 毎セッション読み込まれるのに、リポジトリのどのファイルにも一致しないルール
- モジュールのないエージェントの席、あるいは担当のいないモジュール
- インストールされているのに何にも配線されていないスキル
- 同梱されているのに `settings.json` に登録されていないフック
- 明示的な `model` や `effort` のないエージェント (呼び出し側の料金帯で黙って課金される)
- `Edit` や `Write` を持つレビュアー
- 担当者が存在しない、ボード上のタスク
- 成果物を検査する読み取り専用の席がない、調査またはドキュメントのリポジトリ

三つの実際のハーネスに対して実行したところ、生成されたものは 99、手で保守されていた二つは 79 と 64
でした。低い二つの原因は、毎セッション読み込まれる十八のルールや、タスクボードが追従しないまま
名前を変えられたエージェントの席といったものでした。

## データの出どころ

`.claude/state/harness-graph.json` です。実行そのものが書き出します。スキーマはバージョン管理され、
共有されています。スキルに同梱された Python のスキャナと Rust のツールは、同じリポジトリに対して、
すべてのフィールドを含めバイト単位で同一の出力を生成し、それを `scripts/check_graph_parity.py` が
検査します。食い違う二つのスキャナは、一つのスキャナより悪いからです。

このファイルこそが、概要図で `state` が入口ではなく足元に置かれている理由でもあります。これは実行への
入力ではありません。実行が後に残すものであり、ビューアが読むものです。

## オフにする

ビューアのトグルパネルと `/harness-toggle` コマンドは、同じ契約を書きます。コントロールは
`.claude/disabled/` に移され、その変更はコミットされる `.claude/disabled.json` に記録されます。フックの
`settings.json` 登録もそのまま記録されるので、有効化すればバイト単位で正確に元に戻ります。契約は一つ、
入口は二つです。

安全上重要なコントロールは、クリックではなく、確認フレーズの入力を求めます。エージェントは何も
トグルできません。
