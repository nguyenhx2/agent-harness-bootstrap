# テーラードビルド

[[English|Tailored-Build]] · **日本語**

`spec-builder` は契約で終わります。`harness-bootstrap` はコードベースから始まります。**その間の
ステップで、チームが決まります**。そして、ほとんどのエージェントキットにはこのステップがまったく
ありません。

## 何に答えるのか

エージェントキットの普通の配り方は、全部を配ることです。すべてのエージェント、百のスキル、すべての
ルールとすべてのフックを、誰かがコードベースを読む前にインストールする。気前よく見えます。実際に
起きているのは、見たこともないプロジェクトのために、自分で選んでいないチームを渡されることです。

その代償は、見た目以上に大きいものです:

- **すべてに対して、毎セッションでコンテキストを払う。** リポジトリのどのファイルにも一致しない
  ルールはタダではありません。すべてのリクエストに永遠にかかる税です。
- **持ち主のいない席が生まれる。** 誰も作業を振らないエージェントは、温存された能力ではありません。
  ルーティング表を読みにくくするだけの名前です。
- **助言が一般論になる。** どのリポジトリでも正しくなるように書かれたガイダンスは、あなたの
  リポジトリで行動に移せるほど具体的であることはまれです。
- **何が荷重を支えているのか分からない。** すべてがインストールされていると、どれが選ばれたものかを
  示す手がかりがなく、誰も安全に何かを取り除けません。

網羅性が適合性と取り違えられています。両者は同じものではなく、お金を払う価値があるのは一方だけです。

## 何が何を決めるか

入力はどちらも証拠です。契約は、何を作らなければならないかを、番号付きの要件で示します。
コードベースの分析は、すでに何があるかを示します。編成はこの二つから、そしてそれ以外の何ものでも
なく決まります。

| 何から決まるか | 何を決めるか |
|---|---|
| 実在するモジュール | モジュールごとに dev エージェントを一つ、実在するパスに限定して。モジュールがなければ席もない。 |
| リポジトリの目的 | コード、調査、戦略、ドキュメント、任意の組み合わせ。調査リポジトリには `researcher` と `checker`、ドキュメントリポジトリには `writer` と `checker` が付き、どちらにも使い道のないテストスイートやコードレビューのゲートは付きません。 |
| 契約とあなたの回答 | 18 の席のどれを埋めるか。一回の実行でインストールされるのは **18席のうち3〜17席** で、既定で全部が入ることはありません。 |
| リポジトリ内のマニフェスト | そもそもどのスキルを提案するか。その候補の中からあなたが選び、`/skill-wire` がそれぞれを使うエージェントに接続します。 |
| 実在するパス | どのルールをパス限定にするか。これが、ルール本文の大半を既定のセッションの外に置いておける理由です。 |

## 数字は主張ではなく測定値

最も簡素な回答で足場を組むと 3 席 (ドキュメントまたは調査のリポジトリ) になります。コードの
リポジトリで、データベース、テスト、長期プロジェクトのすべてに「はい」と答えると 17 席になります。

この範囲は、誰かが書き留めた数字ではありません。`scripts/check_numbers.py` が、エージェントを
ゲートするフラグのあらゆる組み合わせについて、**スキャフォルダ自身の選定関数**を使って計算するので、
実際の実行でインストールされるものとずれることがありません。チェッカーの中でルールを再実装すれば、
二つ目の答えを作るだけです。本物を再利用すれば、食い違いは起こり得ません。三回の実際の
スキャフォルド実行と照合し、三回とも一致しました。

どのエージェントをゲートするかを変えればこの範囲も変わり、リポジトリがこの範囲を引用しているすべての
場所は、更新されるまで失敗します。このページも含めてです。

## 発見と配線は別の問題

スキルを見つけることと、それを接続することは同じ仕事ではなく、ハーネスはこの二つを別々に扱います。

**スキル発見 (Skill Discovery)** は、*読んだこともないカタログからは選べない* という問題に答えます。
このプロジェクトのマニフェスト - Python、Ruby、.NET、Java と Kotlin、JavaScript、さらにモノレポの
目印 - を読み、スタックを割り出してから、はじめて提案します。マーケットプレイスのカタログは情報源で
あって、権威ではありません。あなたが選ばない限り、何もインストールされません。

**スキル配線 (Skill Wire)** は、*インストール済みであることは、到達可能であることと同じではない*
という問題に答えます。`/skill-wire` は、選んだスキルを、それを使うエージェントの席やコマンドに接続し、
その接続を文書上の約束事ではなく、グラフのノードとして記録します。繰り返し発生するワークフローに
合うものが何も見つからなければ、`/new-skill` がまず、それがプロジェクトスキルに値するかどうかを判断し
(断るのも普通の結果です)、それから雛形を作り、`skill-check.py` で lint します。見つける、作る、
配線する、の順です。

配線がノードなので、`harness-view` はどのスキルが配線され、どれがディスクに置かれているだけかを
示せます。そして `assess` は、その違いにあなたが気づくのを待つのではなく、所見として報告します。

## 検証できる

誰も持ち主のいない席は、能力ではなくコストです。誰にも使えと言われていないスキル、リポジトリの
どのファイルにも一致しないルールも同じです。`harness-view assess` はこの三つすべてを名指しします:

```bash
harness-view assess .
```

主張を形容詞ではなく数字で述べる意味はそこにあります。「テーラード」は誰でも README に書ける言葉です。
*18席のうち3〜17席、そして席にモジュールがなければこの所見が出る* というのは、検証できることです。
