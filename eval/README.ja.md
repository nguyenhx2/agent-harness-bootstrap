## 結果

`python eval/guardrail_eval.py` -> **250/250 正解 (101 must-block、149 must-allow)。**

**この数字が測っているもの。** eval はハーネスを 1 つ生成し、そこへすべてのペイロードを投げます。そのハーネスでは
特定のフラグが有効になっています。根拠は `guardrail_eval.py` 冒頭の `VARS` ブロックで、現在は `posix`、`ui`、
`db`、`ai`、`ddd`、`tests`、`unit`、`e2e`、`long`、`pr_cli`、`rtk`、`target_cursor`、`hooks_strict` です。
したがってこの数字には、オプトインの strict フック (`hooks_strict`)、長時間セッション用フック (`long`)、
マイグレーションガード (`db`) が含まれます。既定のインストールで入るフックはここで測ったハーネスより少なく、
strict 系のガードで既定で入るのは `guard-destructive` だけです。research と docs の用途は実行中にそれぞれ専用の
スキャフォールドを持ちます。それらを `VARS` に加えると、他のすべてのスイートが前提にしている席の構成が
変わってしまうためです。「250/250」は「このフラグ構成で 250/250」と読んでください。すべてのインストールが
持つ性質ではありません。

件数が 46 から 68 に増えたのは、フックだけでなく `scaffold.py` と `harness-toggle.py` を直接たたく
セキュリティ拒否ケースを一巡追加したためです。内容は、フラグの検証、矛盾する方法論フラグ、HOOK_RUNNER/HOOK_EXT の
導出、`harness-toggle` の大文字小文字を区別しない HARD 階層、空として読まずに中断すべき壊れた隔離台帳、無視すべき
汚染された台帳エントリ、保存済みの登録を復元できないときに安全側へ倒れる `enable`、項目名のパストラバーサル、
不正な `code-graph.json` に耐える 2 つのグラフスクリプトです。[変更点](#変更点) を参照してください。

`--flavor ps1` を渡すと、同じペイロードを `.ps1` フックにも通します (Windows との同等性)。両方のフレーバーを
実行すると **500/500** になります。`PATH` に `powershell`/`pwsh` がない場合は、注記を出して失敗扱いにせず
きれいにスキップします。

ガードレールはフックと `settings.json` の deny ルールです。シェルスクリプト、終了コード、glob マッチで
できています。モデルには一切問い合わせないため、結果はモデルに左右されません。

モデルには問い合わせません。ガードレールはシェルスクリプトなので、結果はモデルに左右されません。
安全の下限はモデルから独立しています。

スイートは逆方向も確認します。ハーネスが正当な作業をブロックしないこと、そして不正なペイロードでフックが
クラッシュしないことです。クラッシュするフックはフェイルオープンになり、フックがない状態より悪い結果になります。
保護しているように見えて、何も守っていないからです。この eval は開発中にまさにそのバグを 2 回捕まえました。
1 回は `jq` がないとき、もう 1 回は WSL 上です。

## 変更点

**セキュリティ拒否の強化 (フレーバーごとに 46 -> 68)。** これらのケースはフックのペイロードを投げるのではなく、
`scaffold.py` と `harness-toggle.py` を直接実行します。既存の `harness-toggle` ケースと同じフレーバー単位の
慣例に従っています (スクリプトの挙動はどのフックフレーバーがインストールされているかに依存しませんが、件数を
揃えるためフレーバーの呼び出しごとに 1 回ずつ実行します)。各ケースは `.eval-workdir/` の下にある使い捨ての
`--target` にスキャフォールドします。例外は実際の隔離状態が必要なケースで、フレーバーごとに共有するリポジトリに
対して実行します (`run_toggle_suite` の後に実行するので、そのクリーンで有効化済みの状態を引き継ぎ、次のケースの前に
自分が変えたものを元に戻します)。

- **`scaffold.py` のフラグ検証**: 未知のフラグ (例: `posx`、`sold_review`) はエラーにその名前が出ます。
  `windows` と `posix` の両方がある場合は拒否、どちらもない場合も拒否します。正しいペイロードは引き続き終了コード 0 です。
- **矛盾する方法論フラグ**: `light`+`tdd`、`light`+`ddd`、`tests` なしの `tdd`、`tests` なしの `unit` は
  すべて拒否します。`light` 単体は引き続き終了コード 0 です。
- **HOOK_RUNNER/HOOK_EXT の導出**: `HOOK_RUNNER` が OS フラグと矛盾する `vars.json` はハードエラーです。
  変数がまったくない場合でも、生成された `settings.json` はフラグに対応する正しいランナーと拡張子を登録します
  (終了コードだけでなく、実際に描画されたフックのコマンド文字列に対して検証します)。
- **大文字小文字を区別しない HARD 階層**: `disable hook/Protect-Secrets` と `disable
  rule/Security-Privacy` (大文字小文字違い) も、入力フレーズを求めて終了コード 2 で拒否し、実ファイルとその
  `settings.json` の登録には手を触れません。これは終了コードだけでなくファイルの状態を検証して証明しています。
  安全チェックの前に `canonical_name()` が大文字小文字を解決することこそが、大文字小文字を区別しない
  ファイルシステムで本来すり抜けかねない仕組みだからです。
- **壊れた台帳での中断**: 不正な JSON を含む `.claude/disabled.json` があると、`harness-toggle.py` は
  どのサブコマンドでも終了コード 1 で中断し、何も変更しません (壊れたバイト列が変わらず、対象のフックファイルが
  一切動かないことを検証)。`scaffold.py` も台帳を黙って空とみなさず、終了コード 1 で終わります。
- **汚染された台帳エントリ**: `kind` が `rule`/`command`/`hook` なのに `from` が
  `.claude/{rules,commands,hooks}/` の外 (例: `.claude/settings.json` や `CLAUDE.md`) を指す
  `disabled.json` エントリは警告付きで無視され、名指しされたアセットは `scaffold.py` によって引き続きインストールされます。
- **復元できない登録での `enable`**: HARD な disable の後で `settings.json` を削除すると (保存した登録を
  復元できなくなる)、`enable` は非ゼロで終了し、`disabled.json` の記録と隔離されたファイルの両方を残します。
  何も失われません。
- **パストラバーサル**: `disable "rule/../../AGENTS"` は非ゼロの終了コードで拒否されます。これは単なる書式
  チェック以上のものです。ガードを外して同じコマンドを作業用コピーに対して再実行したところ、リポジトリルートの
  `AGENTS.md` が実際に `.claude/disabled/rules/AGENTS.md` へ移動しました。項目名の `..` は
  `.claude/rules/../../` を通ってリポジトリルートまで戻ってしまうため、名前の書式チェックだけが、トグルコマンドと
  ハーネス外の実ファイルとの間に立つ唯一の防御です。
- **グラフスクリプトの耐性**: 不正な `.claude/state/code-graph.json` があっても `harness-graph.py` と
  `graph-html.py` はクラッシュしません。どちらも終了コード 0 で出力ファイルを生成します。これは各スクリプトの
  docstring にある「呼び出し元を決して失敗させない」という契約どおりです。

このうち 3 つは、単に通るだけでなく実際に退行を捕まえることを確認しました。ソースファイルの使い捨てコピー
(リポジトリ自身の `scaffold.py` や `harness-toggle.py` ではない) でガードを元に戻し、失敗するはずのシナリオを
そのまま再実行しています。

- `scaffold.py` の `validate_flags()` で未知フラグのチェックをコメントアウトし、`posx` のペイロードを
  再実行: 終了コードが 1 から 0 に変わり、フラグが正当であるかのようにスキャフォールドが完了しました。
- `harness-toggle.py` で `read_disabled()` の `raise CorruptLedger(...)` を `return []` に置き換え、
  壊れた `disabled.json` を持つリポジトリに対して `disable hook/check-commit-msg --yes` を再実行: 終了コードが
  1 から 0 に変わり、フックが実際に隔離されました。壊れた台帳が中断せず、実際の変更を黙って受け入れたことになります。
- `harness-toggle.py` の `parse_item()` から `..`/区切り文字の拒否を取り除き、スキャフォールドしたリポジトリに
  対して `disable "rule/../../AGENTS"` を再実行: 終了コードが 1 から 0 に変わり、リポジトリルートの `AGENTS.md` が
  実際に `.claude/disabled/rules/AGENTS.md` へ移動しました。このトラバーサルが見た目だけの検証漏れではなく、
  実際にファイルを動かすものだと確認できました。

**v1.8.0 の対象 (フレーバーごとに 33 -> 46)。** 3 つの新しいグループを追加し、どれも終了コードだけでなく
実行後のファイル状態を検証します (フレームワークにケース単位の `setup_files`/`delete_files` フィクスチャと、
`file_exists`/`glob_count`/`glob_contains` のアサーションが加わりました)。

- **graph-stale の階層**: `.claude/agents/` 配下を編集すると、再生成された `.claude/state/harness-graph.json` が
  残らなければなりません。docs の編集は `docs-graph.json` に仕込んだ古さのマーカーを置き換えなければなりません。
  どちらも決してブロックしてはいけません。
- **agent-history のレベル**: `off` は何も書かず、`minimal` はインデックス行を 1 行だけ書いて実行ごとのファイルは
  作らず、`summary` は 1,500 文字で切り詰めてトランスクリプトへのポインタを残し、設定がなければ `full` とみなし、
  上限 1 の保持設定では実行ごとのファイルがちょうど 1 つに刈り込まれます (`index.md` は決して消しません)。
- **harness-toggle の安全性**: HARD な項目は、入力フレーズがそのまま与えられるまで終了コード 2 で拒否し、
  ファイルが動かないことを証明します。無効化したフックの settings.json の登録は削除され、他のフックの登録は
  すべて残ります。2 回目の disable/enable サイクルを通しても enable は settings.json をバイト単位で正確に
  復元します。SOFT な項目には `--yes` が必要です。`agent` 種別はそもそも拒否します。

これらを書く過程で、既存の実際のバグが見つかりました。`agent-history.sh` はペイロードの `cwd` とトランスクリプトの
パスを、他のすべてのフックが適用している `norm_path()` のドライブレター変換なしにそのまま使っていました。
Windows の bash では、`C:/` という名前のサブディレクトリに黙ってアーカイブし、自分の設定もトランスクリプトも
決して読めませんでした。フックは現在どちらのパスも正規化します。そうしなければ、履歴のケースは永遠に失敗していたはずです。

**カバレッジ: すべてのブロッキングフックが must-block と must-allow の両方のケースを持つようになりました。** 当時の
5 つのブロッキングフック (`protect-adr`、`guard-main-commit`、`check-commit-msg`、`protect-secrets`、
`guard-agent-spawn`) を両側について監査しました。抜けがあったのは `guard-main-commit` だけで、must-allow の
ケースが存在しなかったため、すべてのコミットを無条件にブロックするよう壊れたフックでもスイート全体を通過して
しまう状態でした。新しいケースは、ペイロードの `cwd` を既定以外のブランチ (`feat/allow-test`、実際のコミット付き。
現行の git では未誕生のブランチで `git rev-parse --abbrev-ref HEAD` が失敗し、黙って別のリポジトリのブランチを
解決する方へ倒れてしまうため) にある兄弟の git チェックアウトに向け、コミットが許可されることを検証します。

このケースは、単に通るだけでなく壊れたフックを実際に捕まえることを確認しました。`guard-main-commit.sh` の
ブランチチェックを一時的に常に一致するようにすると (本来のブランチ比較の代わりに `if true; then`)、ケースは
期待値 0 に対して終了コード 2 で失敗しました。あるべき姿です。このファイルを変更する前にフックは元に戻しています。

効いた設計上の細部が 1 つあります。このケースは当初、兄弟リポジトリのパスを `command` 文字列に埋め込んでいました
(`cd "<dir>" && git commit ...`、または `git -C <dir> commit ...`)。どちらも誤りです。
`git -C <dir> commit` はブランチチェックまで到達すらしません (フック自身のトリガー正規表現は `git` の直後に
`commit`/`push` が来ることを要求し、`-C <dir>` がその間に挟まるため)。また `command` に埋め込んだパスは、
JSON の `cwd` フィールドと違ってフックの `norm_path()` によるドライブレター変換を通らないため、git-bash では
正しく解決されても WSL の bash では壊れます (WSL には `C:/...` ではなく `/mnt/c/...` が必要)。兄弟のパスを
代わりに `cwd` 経由で渡せば両方の問題を避けられ、修正後のケースはそうしています。

**Windows との同等性: `--flavor ps1`。** 既定の実行が試していたのは `.sh` フックだけで、Windows 向けに出荷している
`.ps1` の双子には自動化されたカバレッジがまったくなく、各フックのヘッダーにある同等性契約のコメントしか
ありませんでした。`--flavor ps1` は Windows のフックフレーバー (`HOOK_RUNNER`/`HOOK_EXT` と `windows` フラグ。
CI の `scaffold-matrix` ジョブがスキャフォルダー自体に対して既に行っていることと同じ) で 2 つ目のハーネスを
スキャフォールドし、同じペイロードを `powershell`/`pwsh` 経由で `.ps1` フックに投げます。これは置き換えではなく
追加です。既定の `python eval/guardrail_eval.py` は引き続き `.sh` スイートだけを実行するので、既定のローカル実行も
`eval` CI ジョブ (`--flavor` を一切渡さない) も挙動は変わりません。PowerShell のインタプリタが見つからない場合、
ps1 のパスは理由を表示してスキップされ、実行を失敗させず、`.sh` の結果や終了コードにも影響しません。

**出力。** 人間向けのレポートは、実際に実行したフレーバーごとに `--- POSIX (.sh) ---` / `--- Windows
(.ps1) ---` のセクションに分かれるようになりましたが、最終行の形は変わらず `N/N passed.` のままです。それを grep する
ツールのためです。`--json` の出力には結果ごとの `"flavor"` フィールド (`"sh"` または `"ps1"`) と、任意の
`"ps1_skipped"` 理由文字列が加わりました。`"passed"`/`"failed"` は引き続き、実行したものの合計です。

## この eval が扱わないこと

この eval が測るのは下限 (安いモデルが何をできないようにされているか) であり、上限 (より安いモデルでも良い仕事が
できるか) ではありません。

`benchmark/model_cost.py` は、ある機能のコストが既定の席構成で約 $2.52、すべて Haiku の構成で約 $0.65 だと
教えてくれます。しかし Haiku で作った機能が出荷に値するかどうかは教えてくれませんし、このリポジトリの何をもってしても
わかりません。

それこそが、この主張が成り立つかどうかを決める問いです。

- 良いハーネスによって安いモデルでも許容できる仕事ができるなら、モデルの選択は本当にコモディティ化しており、
  ハーネスこそが戦略です。
- できないなら、依然としてモデルの品質が支配的であり、ハーネスは戦略ではなくコスト最適化にすぎません。

これに答えるには、実際のタスク、実際の評価基準、API キー、そしてあなた自身のリポジトリが必要です。その eval の形は次のとおりです。

1. **フィクスチャタスク** をバックログから用意し、正解がわかっているものにします。根本原因がわかっているバグ、
   受け入れ基準が確定している機能、欠陥を仕込んだ diff などです。
2. **同じタスクを実行** し、生成したハーネスでいくつかの席構成 (既定 / sonnet のみ / haiku のみ) を試します。
   ハーネスは固定し、モデルだけを変えます。
3. **評価基準で採点** します。レビュー席の指標は仕込んだ欠陥の再現率です。開発席の指標は、受け入れ基準を満たすか、
   そしてレビュアーが何か見つけたかどうかです。
4. **差を報告** します。差がゼロのところも含めます。有用な結果は「Opus のほうが良い」ではなく、どの席でどれだけ良いのか、

## 実行方法

```bash
python eval/guardrail_eval.py                # 人間向け、.sh フックのみ
python eval/guardrail_eval.py --json         # 機械向け、1 件でも失敗すれば終了コード 1
python eval/guardrail_eval.py --flavor ps1   # .ps1 フックも実行 (powershell/pwsh が必要)
KEEP_EVAL_WORKDIR=1 python eval/guardrail_eval.py   # 調査用に .eval-workdir/ をディスクに残す
```

完全なハーネスを `.eval-workdir/` にスキャフォールドし、実際に生成されたフックにペイロードを投げ、後片付けをします。
`bash` (常に POSIX のフックフレーバーを試すため) と `git` が必要です。`--flavor ps1` を付けると、1 つ目の横に
Windows フレーバーの 2 つ目のハーネスもスキャフォールドし、同じペイロードを `.ps1` フックに投げます。`PATH` に
`powershell`/`pwsh` が見つからない場合、その部分は注記を表示してスキップされ、実行は `.sh` の結果だけで合格します。
