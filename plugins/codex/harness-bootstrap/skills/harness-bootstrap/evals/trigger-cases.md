# Trigger cases - harness-bootstrap

Re-run whenever the skill's description changes. Each case states what should load, what must stay
quiet, and how the result is judged. `assets/scripts/skill-check.py` requires all six sections and
every field below; whether the answers are good is this file's reader's call.

## positive-discovery

The skill should trigger.

- Request: "Set up agents for this repo - it's a Next.js app with Prisma, we want Claude Code to
  work on it with proper guardrails."
- Repo state: source under `src/`, `package.json`, `prisma/schema.prisma`, no `.claude/` folder.
- Expected skills: harness-bootstrap
- Not expected: spec-builder (specs are not the request), security-audit
- Success criteria: codebase analysis runs first, intake asks one batched questionnaire with the
  detected answers pre-selected, and the scaffold exits 0 with `purpose_code`, `db` and `ui` set.

## negative-discovery

A request that sounds close but belongs elsewhere. The skill must not trigger.

- Request: "Write the requirements spec for our new billing module from these meeting notes."
- Repo state: a bootstrapped harness already exists; `docs/specs/` is empty.
- Expected skills: spec-builder
- Not expected: harness-bootstrap
- Success criteria: no scaffold run, no intake questionnaire; the spec set is written under
  `docs/specs/`.

## edge-case

The skill should trigger and cope with a repo that holds no code.

- Request: "Thiet lap base cho repo nay - it only holds our market research notes and sources."
- Repo state: markdown notes, a `sources/` folder of PDFs, no manifest, no build.
- Expected skills: harness-bootstrap
- Not expected: spec-builder, docs-to-knowledge
- Success criteria: analysis pass 0 proposes `purpose_research`, intake skips the stack, testing
  and DB questions, and the scaffold fields three seats (`orchestrator`, `researcher`, `checker`)
  with no code review or test seat.

## conflict-composition

Several skills look relevant; routing must be explicit.

- Request: "Bootstrap the harness for this repo; we don't have specs yet."
- Repo state: source code present, no `docs/specs/`, no `.claude/`.
- Expected skills: harness-bootstrap leads; spec-builder composes, invoked through the Skill tool at
  intake Q3.
- Not expected: a second copy of the spec structure written by harness-bootstrap itself.
- Success criteria: spec-builder writes `docs/specs/`, harness-bootstrap resumes intake with the FR
  list it produced, and neither duplicates the other's files.

## execution-quality

The skill measurably improves the result.

- Request: "Standardise the .claude folder for this repo."
- Repo state: a brownfield repo with a hand-written `.claude/` (agents without `model:` or `tools:`,
  no hooks).
- Expected skills: harness-bootstrap
- Not expected: none
- Success criteria: every seat has `model`, `effort`, `tools` and `maxTurns`; the hooks are
  registered and fire (block exits 2, pass exits 0); `python .claude/scripts/harness-check.py` exits
  0; user-written files are reported as CONFLICT, never overwritten; `CLAUDE.md` + `AGENTS.md` stay
  under 200 lines with the routing table filled in.
- Baseline (without the skill): agents with inherited models and every tool, no hooks registered,
  no task board - nothing stops a commit to main or a `.env` read.

## efficiency

The skill loads only what it needs.

- Request: "Re-run the harness on this repo - we added a database since the bootstrap."
- Repo state: `vars.json` and a harness generated by this skill exist; a new `prisma/` folder.
- Expected skills: harness-bootstrap, in update mode
- Not expected: spec-builder
- Success criteria: no full intake - only the DB question is asked; the installed `/harness-update`
  drives the run, so `reference/audit-mode.md`, `reference/tech-presets.md` and
  `reference/cost-model.md` stay unread; the scaffold re-run adds the DB seats and reports the rest
  as KEPT.
